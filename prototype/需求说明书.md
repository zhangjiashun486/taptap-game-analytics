## 1.3 项目背景

大数据课程设计要求三人小组完成一个“数据采集与分析平台”：

- 通过爬虫采集真实互联网数据；
- 对采集数据进行清洗与聚类分析（项目周期内无历史数据积累，分析以聚类为主）；
- 构建 Web 服务平台，提供数据展示、用户管理、问答等功能；
- 提供管理端，对采集、清洗、分析过程与结果进行可视化；
- 前端 Vue、Java 提供 Web 服务、Python 负责采集与分析。

本小组选题方向为**游戏内容数据分析**，数据源选择 **TapTap（www.taptap.cn）**——国内知名中文游戏社区与分发平台。TapTap 平台累计上线游戏超过 30 万款；经小组实测，其 Web 端通过公开榜单与标签页面可稳定采集 8000 款以上（截至本稿撰写，已完成闭合爬取，实测 10221 款（覆盖 2259 个标签）），字段包括评分、星级分布、评论数、关注数、热度、标签等，可支撑聚类分析与个性化推荐。

**本系统要解决的核心问题：**

1. 玩家侧：游戏数量巨大（TapTap 累计上线 30 万+），用户“不知道玩什么、怎么找到适合自己的游戏、如何发现相似游戏”；
2. 信息侧：评分、热度、标签等信息分散在不同页面，缺少“按多维度量化对比”的工具；
3. 内容侧：缺少对游戏内容生态的整体视图（哪些类型口碑好、头部与长尾如何分布）；
4. 教学侧：需要用一个真实数据源打通“采集→清洗→聚类→推荐→问答→可视化”的大数据全链路。

# 2. 项目概述

## 2.1 项目目标

构建以 TapTap 游戏数据为内容源的数据采集、分析、展示与推荐平台，目标：

1. 采集 TapTap 公开游戏元数据 ≥10000 条（已完成，实测 10221 款）；
2. 对游戏数据清洗，形成可分析的结构化数据集；
3. 基于评分、热度、关注、标签等特征对游戏聚类，形成可解释分群（口碑神作、热门大作、小众佳作、预约爆款、普通游戏等）；
4. 用户注册登录，记录收藏/浏览/玩过/评分等行为；
5. 结合聚类结果与用户行为提供个性化推荐；
6. 提供自然语言数据问答；
7. 管理端提供采集、清洗、分析过程与结果、平台用户行为可视化；
8. 交付完整文档、原型与可运行系统，通过课程验收。

## 2.2 建设范围

**包含：**

- 数据采集模块（Python 爬虫：TapTap 榜单与标签页，支持断点续传）；
- 数据清洗与存储（MySQL）；
- 数据分析模块（特征工程 + K-Means + 聚类解释）；
- 推荐模块（基于聚类与用户行为）；
- 问答模块（规则检索为主，大模型可选增强）；
- Web 服务平台（Java + Vue）用户端与管理端；
- 可视化（采集流程、清洗过程、分析过程、分析结果、平台用户行为）。

**不包含：**

- 不采集/存储 TapTap 游戏正文、章节、评论全文等受版权保护内容；
- 不实现游戏下载、支付、账号体系与 TapTap 打通；
- 不做需登录 TapTap 账号的功能；
- 不做历史趋势/时序预测分析。

## 2.5 业务流程概述

系统端到端业务流程如下（文字描述，原型阶段补充图示）：

1. **采集**：管理员在管理端触发采集任务 → Python 爬虫按配置采集 TapTap 榜单与标签页 → 解析游戏元数据 → 写入原始表并记录采集日志；
2. **清洗**：对原始数据去重、补缺、标准化 → 生成清洗后数据集并统计清洗指标；
3. **分析**：特征工程 → 确定 K 值（肘部法/轮廓系数）→ K-Means 聚类 → 生成簇画像并落库；
4. **服务**：Java 服务读取游戏、聚类、用户、行为数据，对外提供 REST 接口；
5. **使用**：用户注册登录 → 浏览/搜索游戏 → 收藏/玩过/评分 → 查看个性化推荐 → 使用问答；
6. **管理**：管理员查看采集/清洗/分析可视化与用户行为统计，配置问答引擎。

### 2.6.1 面向玩家用户：解决“找游戏难”

| 用户痛点                      | 本系统提供的能力                 | 对应功能         |
| ------------------------- | ------------------------ | ------------ |

| 有具体问题（“评分 9 分以上的单机游戏有哪些”） | 自然语言数据问答，直接给出答案与数据来源     | FR-06、7.5    |

### 2.6.2 面向内容/运营视角：让内容生态“看得见”

1. 通过聚类把游戏分为“口碑神作 / 热门大作 / 小众佳作 / 预约爆款 / 普通长尾”等类型，回答“什么样的游戏算高质量”；
2. 展示各类型、各标签的游戏数量与特征画像（评分、热度、关注、评论分布）；
3. 支持相同聚类内横向对比（如同为“小众佳作”的游戏差距在哪）；
4. 为“选题/选品/内容推荐”提供数据依据（如某类型是否存在供给缺口）。

### 2.6.3 面向教学与技术：真实数据的全链路实践

1. **数据链路完整**：真实爬虫采集（10,221 款）→ 清洗/归一化 → MySQL 存储 → 聚类 → 推荐 → 问答 → 可视化；
2. **技术栈完整**：Python（采集/分析）+ Java（Spring Boot 服务）+ Vue（前端）+ MySQL（存储）；
3. **算法可解释**：K-Means 聚类配合肘部法则/轮廓系数与簇画像，结果可复现、可解释；
4. **工程规范**：采集断点续传、失败重试、日志与状态可视化，覆盖真实工程问题；
5. **可扩展**：新增数据源或推荐策略时无需改动整体架构。

## 3.1 数据源选择

选择 TapTap 的理由：

1. 中文游戏平台，游戏条目具备“物品”属性，适合聚类、推荐与问答；
2. 公开页面/接口可直接访问，反爬强度在课程设计可承受范围（实测低频爬取未触发风控）；
3. 字段丰富：评分（含版本评分）、星级分布、评论数、关注数、预约数、热度、标签、价格、平台；
4. 教师与同学熟悉游戏领域，演示效果好。

【待确认】若审核认为 8000~12000 条规模不足，可扩展“全部标签+多排序”或更换数据源（备选：天天基金约 2.7 万条，已实测）。

## 3.4 数据清洗需求

1. 以 app_id 去重；同名不同平台按 ID 区分；
2. 缺失处理：评分缺失置空，聚类前剔除或填充；简介缺失不影响分析；
3. 异常处理：星级分布合计与评论总数不一致时以评论总数为准并记录；
4. 数值标准化：Z-Score 或 Min-Max，供聚类使用；
5. 标签清洗：统一大小写、去重、建立“游戏-标签”关联；
6. 清洗过程统计（原始条数、去重数、缺失数、异常数）可视化可追踪。

# 4. 系统总体需求

## 4.1 系统架构需求

三层架构：采集分析层（Python）+ 服务平台层（Java + MySQL）+ 展示层（Vue）。

```
[采集与分析层 Python]
  榜单/标签爬虫 -> 清洗 -> 特征工程 -> K-Means 聚类 -> 结果入库
                  |
[Web 服务层 Java Spring Boot + MyBatis + MySQL]
  用户/行为/游戏/聚类/REST 接口 + 问答引擎
                  |
[展示层 Vue + ECharts]
  用户端（浏览/详情/行为/推荐/问答） + 管理端（可视化）
```

架构要求：

1. 采集、分析、服务可分离运行；爬虫与分析以脚本/任务方式执行并落库；
2. Python 侧产出数据与聚类结果，Java 侧只读并提供接口；
3. 流程均有状态与日志记录，供管理端可视化。

# 7. 数据分析需求

## 7.1 特征工程

1. 数值特征：综合评分、最新版评分、评论数、关注数、预约数、热度、1~5 星人数；
2. 衍生特征：
   - 好评占比 = (5星+4星)/评论总数；
   - 口碑倾向 = (4+5星占比) - (1+2星占比)；
   - 热度关注比 = hits_total / fans_count；
   - 评论密度 = review_count / fans_count；
3. 类别特征：平台、是否付费（独热）；
4. 标签特征：标签频次向量（one-hot 或 TF 加权）；
5. 数值标准化（Z-Score）后聚类；高维时先 PCA（保留 90% 方差）。

## 7.2 聚类算法需求

1. 主算法：K-Means（scikit-learn），K 范围 2~10；
2. K 值确定：肘部法（SSE）+ 轮廓系数，结合业务可解释性；
3. 固定随机种子，结果可复现；
4. 聚类对象：游戏（主）；用户画像聚类（可选）。

## 7.3 聚类结果解释

1. 每个簇：样本数、特征均值画像、代表游戏 TopN、命名建议；
2. 命名规则（示例）：高分高关注=口碑神作；高热度中评分=热门大作；低关注高口碑=小众佳作；高预约未上线=预约爆款；其余=普通/长尾；
3. 结果按 run_id 落库，支持历史对比。

## 7.4 推荐策略需求

1. 相似度：簇一致 + 标签 Jaccard 相似 + 评分差（加权）；
2. 过滤：排除已交互、已下架游戏；
3. 排序：相似度为主，热度/评分为辅；
4. TopN 可配置（默认 10）；
5. 演示评估（可选）：留一法命中率/覆盖率统计。

# 11. 约束与假设

1. 数据为 TapTap 当前快照，不做历史趋势分析；
2. 采集规模受公开页面结构与风控限制，以实测为准（已完成闭合爬取，实测 10221 款 / 2259 标签）；
3. 假设开发与演示环境可访问 TapTap 与 MySQL；无外网环境时采集任务提前执行并导入；
4. 三人按“Python 采集分析 / Java 后端 / Vue 前端”分工，进度安排见《项目计划》；
5. 若 TapTap 页面结构变更，采集器解析层支持快速适配。
